# Contributing to Listen-Fire

## Setting up

You need Docker (for Postgres and Redis), Node 22.23.4 (the version pinned in [`.nvmrc`](.nvmrc)), and pnpm 9.5 or later (the root `package.json` pins `pnpm@9.5.0` as its `packageManager` and declares `"pnpm": "^9.5.0"` in `engines`).

```bash
nvm install && nvm use          # reads .nvmrc
npm install -g pnpm
pnpm install
pnpm --filter api exec prisma generate
```

**Run `prisma generate` before anything else.** `pnpm install` does not produce the Prisma client; `prisma generate` writes it into `node_modules/@prisma/client` from `apps/api/src/prisma/schema.autogenerated.prisma`. Everything that touches the database imports it, including the authorized client checked in under `apps/api/src/generated`, so a fresh clone fails to typecheck and fails to boot until it has been generated once: and the errors name missing modules rather than a missing codegen step. It reads the schema only, so no database has to be running. CI does the same thing immediately after installing.

The dev loop and the integration tests read `apps/api/.env`, which is not in the repository and is not generated for you: copy the example and generate your own secrets.

```bash
cp apps/api/.env.example apps/api/.env
```

[`apps/api/.env.example`](apps/api/.env.example) says which values matter, which can stay as they are, and which two are a one-way door even locally. Nothing else needs the file: a scoped unit test run and a typecheck both work on a clone that has no `.env` at all.

Install the whole workspace, not a filtered subset. `apps/api` typechecks against workspace packages that are consumed as raw TypeScript through symlinks, so a filtered install drops the symlinks and the typecheck fails with unresolved-module errors.

## The dev loop

The dev loop boots the whole stack against real Postgres and Redis and *fake* third-party services, so you can exercise a change end to end without an account anywhere. Slack, Attio, Affinity, email, WhatsApp, Telegram, Airtable, Sheets, Granola, Evertrace, Dealroom and Gmail are all served by [`apps/fake-channels`](apps/fake-channels); the real adapters simply talk to a different base URL when the active team is the dev-loop team, so there is no separate test code path.

```bash
pnpm dev:loop                   # boot the stack; leave it running
pnpm dev:seed                   # provision the dev-loop team (idempotent)
pnpm dev:chat "Set up an ontology to track companies and people"
pnpm dev:inject attio-webhook --event record.updated --object companies --record 1
pnpm dev:inspect attio          # what the fake services now hold
pnpm dev:graph summary          # knowledge graph state
pnpm dev:ui screenshot /model --out /tmp/model.png
tail -F .dev-loop/loop.log      # API and dev-server logs
```

[`docs/dev-loop.md`](docs/dev-loop.md) is the full reference: every CLI, the fake-channels HTTP surface, and worked examples for each inbound path. Read the section you need rather than the whole file.

`pnpm dev:loop:agent` is the same stack on the 3500 port range instead of the 3000 range. It exists so an autonomous coding agent can boot a stack without colliding with a stack a person is already running on the default ports; `dev:loop:agent2` and `dev:loop:agent3` shift again, to 4000 and 4500. Postgres and Redis are shared containers across all of them, so only one agent stack should be running at a time. `pnpm dev:loop:status` shows what is up and prunes dead entries, and `pnpm dev:loop:agent --force-kill` reclaims ports held by a process that died without cleaning up.

## Changing the database schema

The schema is schema-first: `apps/api/src/db/schema.sql` is the source of truth and the migrations are generated from it.

1. Edit `schema.sql` with the change you want.
2. `pnpm -r schema:generate <migration-name>`: diffs the schema and writes a migration file.
3. Edit the generated migration if it needs anything the diff cannot infer, such as a data backfill.
4. `pnpm -r schema:apply`: applies outstanding migrations and regenerates the Prisma and Kysely types. It is idempotent.

Review what step 2 produces before applying it. The generator sweeps unrelated drift into the migration, and on a move between schemas it will author a data-losing sequence rather than a rename.

## Codegen

After changing a tRPC router in `apps/api`, regenerate the shared type package so `apps/web` can see the change:

```bash
pnpm -r codegen:trpc
```

Run `prisma generate` first if you have not already: the tRPC types are emitted by walking the router types, which reference the generated Prisma client.

## Typecheck

```bash
NODE_OPTIONS=--max-old-space-size=8192 pnpm -r code:type-check
```

`apps/api`'s typecheck needs the 8 GB heap. Below it, Node is killed rather than reporting an error, which surfaces as exit code 134 and looks like a hang or a crash rather than an out-of-memory kill. This is what CI runs, and it is the gate that matters most before opening a pull request.

## Tests

Run tests scoped to what you changed. From `apps/api`:

```bash
pnpm test:unit --testPathPattern 'src/interfaces/rest/v1/__test__/require_scope'
pnpm test:unit --findRelatedTests src/interfaces/rest/v1/require_scope.ts
```

Do not run `pnpm test:unit` unscoped. It runs hundreds of test files and evicts the whole Jest cache, which makes every subsequent scoped run slow.

**The unit suites need no database and no configuration.** They mock the integrations they exercise, and [`apps/api/src/test/test-env-defaults.ts`](apps/api/src/test/test-env-defaults.ts) supplies inert values for the environment variables that env-reading modules demand at import time, so a fresh clone can run any scoped unit test as soon as `pnpm install` and `prisma generate` have run. That file loads your `apps/api/.env` first when you have one, and fills in only what is still missing, so a real value never gets replaced by a placeholder.

The integration suites are the ones that need a database. `pnpm test:integration` runs every `*.integration.test.ts`, and each needs `DATABASE_URL_TEST` pointing at a Postgres database *separate from* the dev loop's: the harness applies the migrations to it and the suites write to it freely. There is deliberately no inert default for that variable, because a fake URL would turn a suite that tests nothing into a suite that passes.

`pnpm test:smoke` (also in `apps/api`) is the bounded set CI runs: a unit-only pass over the paths that have broken production before: the engine arbiter, webhook signatures, ask escalation, the file-blob route, dispatch routing, movement execution and the poll worker. It takes about a minute.

The movement language has its own suites, run from its own package:

```bash
cd packages/movement-lang && pnpm test
```

They borrow `apps/api`'s ts-jest transform rather than the package's own jest install, so the whole workspace has to be installed; [`packages/movement-lang/CLAUDE.md`](packages/movement-lang/CLAUDE.md) has the detail.

`pnpm health` at the repository root runs the full local sweep, and `pnpm --filter api verify:local` runs the quick hygiene pass (lint plus unused-export detection). Lint and unused-export checks are deliberately not CI gates; they are local hygiene.

## Working on the language

The parser, checker and type model live in [`packages/movement-lang`](packages/movement-lang). Read [`packages/movement-lang/CLAUDE.md`](packages/movement-lang/CLAUDE.md) before changing any of them. It carries the two questions that have repeatedly turned a proposed feature into a deletion: "what is the simplest way to solve this using the structure of the graph?" and "what would TypeScript do?": along with the invariants that keep costing time when they are ignored: the type system is structural rather than nominal, a magic string is one that gets parsed rather than compared, and silent degradation is the absence of a guarantee rather than a weaker one.

## Commits

Commit subjects follow conventional-commit style: a type, an optional scope in parentheses, a colon, then a lower-case statement of what the change does. Recent examples from `git log`:

```
fix(trpc): regenerate the shared types against a generated Prisma client
feat(api): the watchdog names the frame that is blocking the loop
docs: point DEV_LOOP.md references at its new docs/dev-loop.md location
chore(brand): the sans face is the reader's own, not a licensed one
```

Write the subject as a fact about the resulting code, not as an instruction. Comments in the code explain *why*, never *what*.

A pull request that changes what an operator sets or an author writes adds a line under Unreleased in [`CHANGELOG.md`](CHANGELOG.md), in the same pull request.

## Claude Code

The maintainers develop this repository with Claude Code. [`CLAUDE.md`](CLAUDE.md) at the root is the instruction file it reads, and [`.claude/skills`](.claude/skills) holds the repo's packaged procedures: currently the schema-migration walkthrough and the batched pre-push gate. Both are checked in, so a contributor using Claude Code gets the same workflow the maintainers do; neither is required if you are not using it.
