# Migrating to Steady Lynx (3)

Language version 3, **Steady Lynx**, arrives in v0.10.0. The release's [changelog entry](../../CHANGELOG.md) lists each change in a line; this guide carries the full detail, grouped by topic. Every rule here that says "under Steady Lynx (3)" applies only to an automation pinned to version 3. Quiet Heron (1) and Bright Otter (2) keep their old behaviour, except where a rule says it applies under every version.

## 1. How the pin moves

- Language version 3 arrives: **Steady Lynx**. A new automation is written in it, and the deploy check moves an automation up to it when it validates cleanly there. It reads a list literal exactly, which refuses programs Bright Otter (2) accepted, so those stay on their version until repaired and upgraded.
- An automation that does not validate under Steady Lynx (3) is shown with the **Review** badge, and the automation page lists the diagnostics (see the v0.8.0 entries in [`docs/changelog/v0.8.md`](../changelog/v0.8.md) for the deploy check and `upgradeAutomation`).

## 2. List literals are tuples

- Language version 3, **Steady Lynx**, reads a list literal as the tuple it is. Why: an index read off a literal was checked against what its members share, so `AT(["a", 1], 0) * 2` multiplied text, `AT([{ a: 1 }, { b: 2 }], 0)` looked up a key the first dict was never written with, and a walk off `AT([one, two], 1)` took an edge the second record has not got, all without a word; and a literal whose members share no type was a list nothing checked, so `[o.name, o.amount]` written into a list of numbers reached the system. Under Steady Lynx each of these is refused at save (`MOV_ARITH_NON_NUMERIC`, `MOV_DICT_UNKNOWN_KEY`, `MOV_TRAVERSE_UNKNOWN_EDGE`, `MOV_WRITE_FIELD_TYPE`, and the comparison and json rules for a member that may be text, a number or json). The run is unchanged: a version-2 automation that validates under Steady Lynx does exactly what it did, so the move needs no warning beyond these refusals.
- A list literal is typed as a tuple, one slot per member, under language version 3 (**Steady Lynx**): `[m.Subject, file]` is `[text, file]`, and `AT(t, 0)` reads the first slot exactly, always present. With a spread it is a variadic tuple, `[text, ...list of file]`. Anywhere a list is expected (`MAP`, `FILTER`, `JOIN`, a list-typed field or parameter) a tuple reads as a list of its members' union, as TypeScript reads `[string, number]` as `(string | number)[]`: `[o.name, o.amount]` is a `list of (number | text)`, so `JOIN([o.name, o.amount], " ")` validates and writing it into a list of numbers is refused. A literal holding both records and values (`[company, "label"]`) is accepted as a tuple; `MOV_LIST_MIXED` fires where it is read as a list, such as `MAP(both, …)` or a write into a list field. An automation pinned to Quiet Heron (1) or Bright Otter (2) keeps the list typing it had: a literal is the list its members share, an index read off one is that type or absent, and members that share nothing read as a list nothing checks.
- `await parallel([...])` and `await race([...])` with arms whose results differ read as a list of their union under Steady Lynx; before, they read as a list nothing checks.

## 3. Calls and the standard library

- Under Steady Lynx (3) a call is resolved the way a name is: the movement's own scopes first, then the file and its imports, then the standard library, which lists every built-in with what each argument takes, what it gives back and what it does (calls a model, reads the clock, reads a file). Why: before, a built-in's arguments were never checked and an unknown function name was a call nobody checked, so `UPPER(company)` wrote `[object Object]` and a misspelt `UPPPER(x)` failed only when the movement ran. Each of these is now refused at save:
  - An unknown function name is `MOV_FUNCTION_UNKNOWN`, with the closest function or built-in suggested. Inside a write field an unknown name is still accepted, because the target field may offer functions of its own (a Slack message's `SLACK_MESSAGE(…)`) that the save check cannot list yet.
  - Function names are case-insensitive: `upper(x)`, `UPPER(x)` and `Upper(x)` are one built-in, and `Email_To_Doc(m)` calls `email_to_doc`. Two functions (movements, plugins or imported functions) whose names differ only by letter case, or a function named like a built-in in any case (`movement sum(…)`), are `MOV_FUNCTION_NAME_COLLISION`. Variable names keep their case, and a variable holding a value shadows a built-in as TypeScript's does: `upper = 3` then `upper(x)` is `MOV_CALL_NOT_MOVEMENT`. A name bound to a closure is a function's name (see [Functions](#7-functions)), so `upper = (t) => t` is `MOV_FUNCTION_NAME_COLLISION`.
  - A built-in's argument of the wrong kind is `MOV_BUILTIN_ARG_TYPE` (`ROUND(m.Subject)`); a record where a value is read is `MOV_RECORD_NOT_A_VALUE` and a json value `MOV_JSON_OPAQUE`, as everywhere else (`UPPER(company)`, `UPPER(c-[p:Members]->)`). The wrong number of arguments, or a function or type handed to a built-in that takes values, is `MOV_BUILTIN_ARGS`.
  - A built-in's call is typed by what it gives back, so `UPPER(x)` is text and writing it into a number field is `MOV_WRITE_FIELD_TYPE`. Before, such a call had no type and every rule downstream of it was silent.
  - A call written inside another expression is the value it gives back (see [Nested calls and evaluation order](#4-nested-calls-and-evaluation-order)). Inside a walk's `WHERE`, `ORDER BY` or settings, which are read once per landing, a movement's call, `MAP`, `FILTER`, `REDUCE`, `GROUPBY`, `KEYBY` or `MEMBERS` is refused as `MOV_CALL_NESTED`, with the binding to write. This now includes the hops heading a block (`c-[m:Members WHERE f(m)]-> { … }`), whose calls were not resolved at all before. A built-in that only computes a value, written as a statement on its own (`UPPER(x)`), is `MOV_BUILTIN_UNUSED`.
  - `listen to … fire <movement>` and `callback(<movement>(…))` name the movement in any letter case, as a call does.
  - A run does what it did: a call the save check accepts reads exactly as it did before. The collection ops and `MEMBERS` are now ordinary calls rather than forms of their own, so their errors are reported by the save check rather than as parse errors. A built-in's declared effects now count towards a movement's effect row under every version, so a `READ(file)` shows as reading files and a retired `KG_VALUE(…)` as reading the knowledge graph.
  - Under Quiet Heron (1) and Bright Otter (2) the language does not change: names keep their case, an unknown function and a built-in's arguments stay unchecked, and a built-in's call stays untyped. Only the effect row above is shared by every version.
- Under Steady Lynx (3) a movement's call, a closure's call, `MAP` and the other collection ops, or `MEMBERS` written inside `SORT`'s key is refused as `MOV_CALL_NESTED`. Why: the key is read once per member, but a call there ran once, where it was written, so every member sorted by the same answer. Work the key out per member first (`MAP`), then sort by it. A value built-in in the key (`SORT(people, LENGTH(Name))`) is read per member as before. The key is the only built-in argument read per member. Under versions 1 and 2 nothing nests, and nothing changes.
- `first(c-[m:Members]->).Name` reads the field of the landing the aggregate picks, in any letter case, as `FIRST(…).Name` always did. Before, the lowercase spelling was refused. This applies under every language version, since it accepts only what was refused before.

## 4. Nested calls and evaluation order

- Under Steady Lynx (3) a call nests inside any expression, because a function's arguments are ordinary expressions and a movement is a function: `double(n) + 1`, `ONLY(extract(content, Company))`, `COUNT(MAP(xs, f))`, `MAP(MAP(xs, f), g)`, `log(MAP(xs, f))`. A nested call means exactly what binding it to a name first and reading the name means, and it is checked and typed that way: `label(x)` that returns text is refused written into a number field. Its effects count towards the movement around it. How it runs:
  - Left to right, as the text reads. Every operand before a nested call is read before the call runs, and a call's arguments are all evaluated before its body runs: `CONCAT(mark("a"), mark("b"))` writes `a` then `b`.
  - `IF`, `AND`, `OR` and `COALESCE` short-circuit, as TypeScript's `?:`, `&&`, `||` and `??` do: an operand they do not need is never evaluated, so a call in an arm that is not taken never runs and its writes never happen. There is no restriction on effects in those arms.
  - A call that may wait (a movement that `await`s) is refused inside an expression as `MOV_NESTED_CALL_SUSPENDS`: a wait parks the run where it is written, and a position inside an expression has nowhere to come back to. Call it on its own line and use the name.
  - Under Quiet Heron (1) and Bright Otter (2) nothing nests; those versions have no positional calls.
  - A field reads off any call's result, as it reads off a name: `ONLY(extract(content, Company)).name`, `FIRST(people).Name`, `extractOne(content, S).summary`. Before, a field read off a built-in's call was `MOV_EXPR_PARSE`. A call whose result may be absent gives a field that may be absent (`T | absent`). Under versions 1 and 2 it stays the parse error it was.
- Under Steady Lynx (3) `COALESCE(a, b, …)` stops at the first argument that has a value and never evaluates the rest. Before, every argument was evaluated first and then the first present one chosen, so a later argument could still call a model, read a file, or fail the run (`COALESCE(x, ONLY(list))` failed whenever `list` held two values, even with `x` present). A saved automation keeps the old order until it moves to version 3.
- Every expression is now read by one grammar that builds a structured tree, in the save check and when the movement runs. Before, a layer rewrote expression text before a second grammar parsed it. What an expression means is unchanged apart from the fixes in the [appendix](#appendix-every-version-changes-in-full) and one widening: a bare walk (`c-[m:Messages]->`) is the records it lands on wherever a value goes, such as `COALESCE(c-[m:Messages]->, [])`, `[c-[m:Messages]->]` or `count(c-[m:Messages]->)`. Before, a bare walk was accepted only as a whole expression or as the first argument of an upper-case aggregate, and refused everywhere else. `EXISTS(walk)` still tests that the walk lands anywhere, and `walk.field` still reads a field. This applies under every language version, since it accepts only what was refused before.

## 5. Absence and narrowing

- Under Steady Lynx (3) a value that may be absent no longer fills a graph literal's required field without a word. Why: `details = ONLY(extract(…))` then `graph<Merged> { summary: details.summary }`, with `summary: <text>` declared, saved and ran when the extraction found nothing, and the graph held no `summary`. Three layers were each silent: a field read off a record that may not be there was typed as present, a graph literal's field took a value that may be absent, and the run left an absent value out of the graph instead of failing. Now:
  - A field read off a record that may not be there (`ONLY(…)`, `FIRST(…)`, `AT(rows, 0)`) is `T | absent`, as TypeScript types `r?.x`, and a `!= null` guard on the record narrows it.
  - Such a value written into a graph literal's required field, directly or through a spread, is `MOV_ABSENT_REQUIRED`, with the fix: fall back with `COALESCE`, or declare the field `<T | null>`. This is the rule a write field and a required parameter already follow.
  - A graph literal with a shape is checked against it when it is built, so a required field that turns out absent anyway fails the run, naming the field. Before, only a graph that took keys from a map was checked.
  - Under versions 1 and 2 each keeps its old behaviour exactly.
- Under Steady Lynx (3) an early `return` narrows what follows it, as `ERROR(…)` already did and as TypeScript does: after `if t == null { return "none" }`, `t` is present for the rest of that body, so `Name: t` is no longer refused as `MOV_ABSENT_REQUIRED`. Why: builders reach for the return form and lost a save round to the refusal. Every presence test narrows this way (`x == null`, `ISNULL(x)`, `NOT EXISTS(x)`, `a == null OR b == null`), and so does the other direction: `if t != null { … } else { return "none" }` leaves `t` present after the `if`, as does any `if … else` where the `else` and every arm but one leave. A `return` inside an arm leaves the nearest body (a movement, a closure, or one turn of a block), so the narrowing holds for the rest of that body only. The run is unchanged: a `return` already stopped its body. Under Quiet Heron (1) and Bright Otter (2) only `ERROR(…)` narrows, as before.
- Under Steady Lynx (3) a test on the left of `AND` or `OR` narrows the right side, as TypeScript does: `f.Headcount != null AND f.Headcount > 50` and `f.Headcount == null OR f.Headcount > 50` are no longer refused as `MOV_ABSENT_REQUIRED`. Why: builders wrote the natural guard and lost a save round to the refusal, then reached for `COALESCE(f.Headcount, 0) > 50`. The right side of `AND` is checked as if the left held, and of `OR` as if it failed; the presence tests are the ones an `if` already honours (`x != null`, `x == null`, `EXISTS(x)`, `ISNULL(x)`, `NOT …`), and they compose through nesting and `NOT (…)`. It applies wherever a condition is written: a binding, an `IF … THEN … ELSE … END`, an `if` statement, a hop's `WHERE` (its bare fields and its alias's) and a function's body. The guard proves a field of a record, a record that may be empty, a dict key, or a bound value; inside `IF … THEN`, a field guard now narrows the `THEN` side too. The run is unchanged: `AND` and `OR` already stop at the first operand that settles the answer, so the right side never runs where the left rules it out. Under Quiet Heron (1) and Bright Otter (2) each operand is checked alone, as before.
- Under Steady Lynx (3) `d.key` off a dict is the lookup `AT(d, "key")` is: it reads the key's own type, and a key a dict written in braces does not have is `MOV_DICT_UNKNOWN_KEY`. Before, the read had no type, and it was checked against any name `key` in scope instead. The run is unchanged; under versions 1 and 2 the read stays unchecked.
- Under Steady Lynx (3) `await sleep(…)` reads as a boolean once woken, so `x = await sleep(1h)` then `x == true` checks clean; before, it was untyped and the comparison was `MOV_COMPARE_TYPE_MISMATCH`. The run is unchanged (a woken sleep already bound `true`); Quiet Heron (1) and Bright Otter (2) keep the old reading.

## 6. Retired and refused forms

Each is refused at save under Steady Lynx (3), with what to write instead.

- Under Steady Lynx (3) three things the expression grammar did without a word are refused at save:
  - `JOIN`'s separator written as anything but text in place (`JOIN(xs, sep)`, `JOIN(xs, "${sep}")`) is `MOV_BUILTIN_ARGS`: it was dropped and `", "` used instead. (An aggregate's extra argument, `COUNT(xs, 3)`, which read only `xs`, is already `MOV_BUILTIN_ARGS` by the argument count rule in [Calls and the standard library](#3-calls-and-the-standard-library).)
  - `IF … THEN … END` with no `ELSE` is `MOV_IF_WITHOUT_ELSE`: where the condition failed it was `""`, whatever `THEN` held, so `IF x THEN 3 END` was a number or empty text and had no type at all. Write the `ELSE`.
  - A `KG_EXISTS` or `KG_VALUE` query written as anything but text in place (`KG_EXISTS(q)`, `KG_EXISTS("MATCH … ${x}")`) is `MOV_BUILTIN_ARGS`: it was read as an empty query. Write the query out and pass its values as parameters (`$0`, `$1`, …). Both functions remain retired in the movement engine; query the graph by walking it.
  - Under versions 1 and 2 each keeps its old behaviour exactly.
- Under Steady Lynx (3) three more things a walk or a value dropped without a word are refused at save:
  - Settings `{ … }` on a hop (`c-[m:members { limit: 3 }]->`) are `MOV_HOP_CONFIG_UNREAD`: no hop reads settings, so they were dropped. (`#transform`, the one hop that read them, is retired; see below.)
  - A walk ending in `-[:_resources]->` that would lose part of what was written is `MOV_RESOURCE_WALK_UNREAD`. As a value (`msg-[:_resources]->.url`), its root was dropped, so it read from no record. As a block head with hops before the resource hop (`c-[m:members]->-[f:_resources]-> { … }`), only the hops before it were walked. A one-hop block head (`msg-[f:_resources]-> { … }`) is unchanged: it reads its root.
  - `LLM_AGG(…)` is `MOV_BUILTIN_NOT_RUN`. Why: the movement engine cannot run it, so a saved call failed the run, and its instruction never reached a model. Join the members and call `AI(…)` on them instead.
  - Under versions 1 and 2 each keeps its old behaviour exactly.
- Under Steady Lynx (3) four expression forms from the translation graph are retired, each refused at save with the form to write instead. Why: each reads something a movement run does not have, so it failed the run or read nothing, without a word at save.
  - The `-[t:#transform { plugin: … }]->` hop is `MOV_TRANSFORM_HOP_RETIRED`: the movement engine never ran it, so the run failed. Import the plugin and call it with the value it reads: `import { fetch_url } from plugins`, then `page = fetch_url(url: m.u)`. The message names the plugin the hop's settings name, with its required arguments.
  - The `-[#linked WHERE type = "…"]->` hop is `MOV_LINKED_HOP_RETIRED`, in every form, rooted or not. Keep the write's handle and read from it (`rec = write crm-[:Companies]-> { … }`, then `rec.<field>`), or tie a write to a record you hold with `write … bind other { … }`.
  - `@parent.created` and `@parent.external_id` are `MOV_PARENT_READ_RETIRED`: they read the translation graph's parent result. Write the child off the parent write's handle: `co = write crm-[:Companies]-> { … }`, then `write co-[:Team]-> { … }`.
  - `@resource.<field>` is `MOV_RESOURCE_READ_RETIRED`. Inside a `-[f:_resources WHERE …]->` filter it is the field's bare name, and the diagnostic carries that exact rewrite (`WHERE @resource.type == "URL"` becomes `WHERE type == "URL"`). Anywhere else it was always empty, so there is nothing to rewrite it to. The `_resources` hop and bare field names in its filter are unchanged.
  - These replace `MOV_META_FIELD_UNKNOWN`, which checked the field `@resource` and `@parent` named, and the `#linked` half of `MOV_RESOURCE_WALK_UNREAD`.
  - Under Quiet Heron (1) and Bright Otter (2) each keeps its old behaviour exactly.
- A write inside a function handed to `MAP` (or another built-in that takes one) is now checked at save like the same write outside it. Before, a type reached only by walking from a record written inside the function (`write record-[:Lists]-> { … }`) was never described, so any field written to it was accepted. This applies from language version 3; a movement pinned to version 1 or 2 is checked as before.

## 7. Functions

- Under Steady Lynx (3) a movement is called with its arguments in order, as TypeScript calls a function: `doc = email_to_doc(msg)` and `log_doc(email_to_doc(msg))` bind each argument to the parameter declared in its place. Named calls (`email_to_doc(m: msg)`) are unchanged. One call is all positional or all named: a mix is a parse error. Too few or too many arguments is `MOV_CALL_ARITY` (with `MOV_CALL_ARG_MISSING` naming what is missing), and a type mismatch names the parameter the argument binds (`for 'count' (argument 3)`). A positional invocation is a call whatever it names; when the name is a built-in, `x = UPPER(m.Subject)` is the value it computes, exactly as before (see [Calls and the standard library](#3-calls-and-the-standard-library)). A plugin's arguments stay named, because its parameters have no designed order: `fetch_url("…")` is `MOV_PLUGIN_ARGS_NAMED`. Under Quiet Heron (1) and Bright Otter (2) a positional argument is still the parse error it was.
- Under Steady Lynx (3) a movement parameter can take a value rather than a record: a scalar (`<text>`, `<number>`, `<boolean>`, `<date>`, `<datetime>`, `<file>`, `<json>`), a declared refinement (`<Tone>`), a list (`<text[]>`), or a config record spelled as a TypeScript object type (`cfg: <{ mode: text, owner?: text }>`). The argument is any expression, and it is checked as TypeScript checks one: a record literal may not carry a key the parameter does not declare (with a did-you-mean), a required key may not be missing, a string literal against a refinement must be one of its values, and a value that may be absent does not fill a parameter that requires one. Inside the movement an optional key reads as possibly absent (`AT(cfg, "owner")` needs `?:` to be written). A listener cannot fire a movement whose parameter takes a value (`MOV_LISTEN_PARAM_MISMATCH`), and a callback's fire-time parameter stays a single scalar. Under versions 1 and 2 a scalar-typed movement parameter is still refused as before.
- A value passed to a parameter that takes a record (`persist(c: msg.Subject)` where `c: <Lead>`) is refused at save as `MOV_CALL_ARG_TYPE` under Steady Lynx (3). Such a call always failed when it ran (`passing a value binding as a movement argument`); now it is said where it is written. An automation pinned to version 1 or 2 keeps the run-time refusal.
- Under Steady Lynx (3) a closure can have an expression for its body, as TypeScript's can: `(v) => v * 2` is `(v) => { return v * 2 }`. So a function written in place is a value like any other, bound (`inc = (v: <number>) => v + 1`) and passed (`MAP(xs, inc)`, `MAP(xs, (t) => UPPER(t))`). Under versions 1 and 2 a closure body is still a block.
- Under Steady Lynx (3) a closure bound to a name is called like any function, because movements and functions are the same thing: `inc = (v: <number>) => v + 1` then `inc(2)`, `inc(v: 2)`, `double(inc(x)) + 1`, or `note(m.Subject)` on its own line. Before, the call was refused as `MOV_CALL_NOT_MOVEMENT`. How it reads:
  - Its parameters check the arguments (`MOV_CALL_ARITY`, and the argument type rules a movement's call has), and the call is typed by what its body returns.
  - Calling it does what its body does: a model call or a write in the body counts towards the movement that calls it. Binding it does nothing.
  - Its name is a function's name: it is called in any letter case (`INC(2)`), and naming it like a built-in (`upper = (t) => t`) or like another function in another case (`Double = …` beside `movement double`) is `MOV_FUNCTION_NAME_COLLISION`. A name holding a value is still not callable.
  - A closure that may wait is called on its own line, as a movement that may wait is, and refused inside an expression (`MOV_NESTED_CALL_SUSPENDS`); it can also be passed as an arm of `await race([…])` or `await parallel([…])`.
  - Under versions 1 and 2 a closure is passed, never called, as before.
  - Binding the call of a closure whose body returns nothing is `MOV_CALL_RETURNS_NOTHING`, as binding such a movement's call is: `log = (t: <text>) => { write … }` then `x = log("hi")` is refused, and so is a closure binding its own call (`y = tick(n - 1)`). Before, such a binding was silent and bound nothing.
- Under Steady Lynx (3) a function may call itself, directly or through other functions, and a closure bound to a name may call itself by that name. Why: walking a tree, an org chart or a chain of records needs it, and movements are functions. Before, every version refused a call to a movement already running, at run time. How it reads:
  - A function declares what it returns after its parameters, as TypeScript writes it: `function fact(n: <number>): <number> { … }`, `movement f(…): <{ total: number }> { … }`, `f = (n: <number>): <number> => …`. The type is written as a parameter's is. It is optional on any function, and every `return` is then checked against it (`MOV_RETURN_TYPE`, which also refuses a function that declares a type and never returns), and a call is typed by it.
  - Every function that calls itself, directly or through others, must declare it, as TypeScript requires: what its body returns cannot be worked out from a body that needs its own answer. Leaving it out is `MOV_RECURSIVE_RETURN_TYPE`, naming the loop (`'ping' calls itself through 'pong' (ping → pong → ping)`). A recursive function that returns no value has nothing to declare.
  - Functions that call each other in a loop share one effect row: what any of them does (writes, reads, model calls, waits) counts for all of them.
  - Calls nest at most `MOVEMENT_MAX_CALL_DEPTH` deep (default 32; see [Cost cap and call depth](#12-cost-cap-and-call-depth)). The run's own movement is not a call; each call by name is one level, including a function handed by name to `MAP` or to `race`/`parallel`; a function written in place inside `MAP` is not, as it has no name to call itself by. Items of one `MAP`, and arms of one `parallel`, run side by side, so each counts its own depth.
  - Every level runs inside the same run, never a new one: it spends against the same cost cap, and a wait or a cost cap pause deep inside a recursion resumes exactly there.
  - A run that resumes counts the calls it is inside as it did before it stopped, including a function handed by name to `MAP` or named as a `race`/`parallel` arm. Before, such a level was not counted after a resume, so a resumed recursion could nest one call deeper than the limit for each of them.
  - Under Quiet Heron (1) and Bright Otter (2) nothing changes: there is no return type syntax, and a call to a movement already running fails the run as it always did (`recursive movement calls (…)`).

## 8. Extraction as a function

- Under Steady Lynx (3), extraction is also a function: `companies = extract(content, Company, { tier: 'careful' })` reads a list of text and files and hands back a list of `Company` records, one per thing found. The `extract … from [ … ] { … }` keyword is unchanged: its prompts are byte for byte what they were, and it keeps its own engine path.
  - The content is a list, read in order: text, files (read as text, as the keyword reads them), and records rendered as text with `TEXT.SERIALISE(record, 'JSON')`. A record, map, json, number or date put in raw, a list inside the list (spread it with `...`), or one value where the list goes is refused at save as `MOV_EXTRACT_CONTENT`, naming the fix.
  - The shape is a node declaration: at file level, declared in the body around the call (a node declaration inside a function or lambda body now runs), or written in place with its header, `extract(content, node Person: "each person named" { name: <text> "their name" })`. Anything else is `MOV_EXTRACT_SHAPE_COMPUTED`; the anonymous `node { … }` literal is a parse error, because its strings are values, not descriptions.
  - The records read as an extracted record of the same declaration reads under the keyword (text `""` when nothing was found, a typed field `T | absent`, `<text | null>` null), walk their nested nodes with `WHERE`, take writes and links as any record the run built, and fit `MAP`, `ONLY` and `TEXT.SERIALISE`. Each field's evidence records which content item it came from, on the run's write provenance.
  - Settings are `tier`, `model` and `effort` (`'low'`, `'medium'`, `'high'`, `'xhigh'`), each written as a quoted word; a named model or effort wins over the tier's assignment on this deployment (`EXTRACTION_TIERS`). An unknown key (with a did-you-mean), a word outside its set, a computed value, or a model this deployment cannot reach is refused at save as `MOV_EXTRACT_CONFIG`.
  - It is a value like any other: bound (`found = extract(…)`), returned, or written inside another expression (`ONLY(extract(…))`, `MAP(extract(…), f)`). Inside a walk's `WHERE` it is refused as `MOV_EXTRACT_CALL_NESTED`, because the `WHERE` is read once per landing. On its own line as a statement it is a parse error.
  - A declaration's name read as a value is the declaration: `S = Company` then `extract(content, S)` fills `Company`.
  - A reply that does not fit the shape is asked once more and then fails the call; inside `MAP`, `onError` decides what that member does.
  - The prompt is laid out for the provider's prompt cache: one system prompt shared by every extraction call, each content item as its own block in the author's order, and the shape and instructions last. The engine remembers the content it has sent in a run and marks the end of the longest prefix a call shares with an earlier one, and the end of all its content, as cache breakpoints (Anthropic; other providers keep the order and drop the marks). Each call's trace entry carries the breakpoints and the provider's cache read and write tokens.
  - Under Quiet Heron (1) and Bright Otter (2), `extract(` stays the parse error it was.
  - Its name is case-insensitive like every function's: `EXTRACT(…)` and `Extract(…)` are the extraction call. Before, any spelling but `extract` was refused as `MOV_BUILTIN_ARGS`. The keyword (`extract from […]`, `extract "careful" from […]`) is unchanged, since it is never followed by `(`.
- Under Steady Lynx (3), `extractOne(content, Shape, settings)` extracts the single record the content describes, as TypeScript's `find` sits beside `filter`: `details = extractOne([...content, TEXT.SERIALISE(c, 'JSON')], CompanyDetail, { tier: 'careful' })`. Why: `ONLY(extract(…))` asked the model for each one and then counted; this asks it for the one, so the shape's description names that one thing (`"the company"`).
  - It gives back `Shape | absent`, handled as `ONLY(extract(…))`'s result is: a typed field read off it is refused where a value is needed until it is `COALESCE`d or guarded (`MOV_ABSENT_REQUIRED`), and it spreads (`{ ...c, ...details }`) and fills a graph literal under the same rules.
  - The model is asked for "the single one these sources describe, or nothing if they don't", in the shape's own description, and answers one record or null. A reply naming several is a reply that does not fit: it is asked once more, then the call fails (`onError` in `MAP` decides what that member does). A record with nothing in it is absent, and the run's trace keeps the model's reply beside it.
  - Content, settings, evidence, cost and the prompt-cache layout are `extract`'s; only the last block differs, so an `extractOne` per record reads the content a root `extract` over the same content already cached.
  - It is nestable (`COALESCE(extractOne(content, S).employees, 0)`), refused inside a walk's `WHERE` (`MOV_EXTRACT_CALL_NESTED`) and on its own line, and its name is case-insensitive like every function's. `extract` still gives each record, as a list.
  - Under Quiet Heron (1) and Bright Otter (2), `extractOne(…)` is the ordinary unknown name it always was.
- `EXTRACTION_TIERS` lets a deployment choose the model and effort behind each extraction tier (`quick`, `careful`, `thorough`), as a JSON object such as `{"careful": {"model": "claude-opus-5", "effort": "medium"}}`. Unset, nothing changes: every tier is `claude-sonnet-5` at effort `low`, `high` and `xhigh`, and an extraction with no tier keeps choosing its model by how many kinds of record it reads, at effort `low`. The model is routed by `MODEL_MAP` like any other, and boot refuses a tier, field or model it cannot serve, including a model this deployment has no credentials to call.
- An extraction shape with a field and a child node of the same name (an `extract … from` block, a `node X: "…" { … }` declaration, or the shape of `extract(content, Shape)`) is now refused at save as `MOV_EXTRACT_FIELD_DUPLICATE`. Before, it saved and failed when a record of it was written out.

## 9. Graph literals and spreads

These apply under every language version.

- Graph literals build a local graph as a value: `graph<Message> { text: m.Body, attachment: m-[a:Attachments]-> { name: a.Name, type: a.Type, file: a.\`File\` } }`. In the modern spelling `node` only declares a shape and `graph` only builds a value; the anonymous `node { … }` literal is unchanged.
  - With a shape the literal is checked like TypeScript's `satisfies`, and the value is then of the shape. A misspelt field is `MOV_GRAPH_FIELD_UNKNOWN` (with a did-you-mean), a mistyped one `MOV_GRAPH_FIELD_TYPE`, a field where the shape has a child node (or the reverse) `MOV_GRAPH_ENTRY_KIND`, and a required field never written `MOV_GRAPH_FIELD_MISSING`. A `<T | null>` field may be left out; it is then absent and reads as `T | absent`. A shape that is not a node declaration is `MOV_GRAPH_SHAPE`.
  - `graph { … }` with no shape takes its type from the literal.
  - `graph<Shape> {}` is the typed empty graph. It is valid when the shape requires no field. Its child nodes start empty: an edge holds zero or more records, as every other structural check already reads it.
  - The body uses a write body's field syntax. `{ … }` is a child node and `[{ … }, { … }]` several. A walk followed by a field body builds one child per record on the walk.
  - Entries follow TypeScript's object semantics: `{ items: obj }` holds a reference and `{ ...obj }` copies. A bare walk (`attachment: m-[:Attachments]->`) or a record written as an entry's value (`owner: r`, `owner: ONLY(m-[:Owner]->)`, or a list of records such as what a `MAP` of writes hands back) holds REFERENCES to the real records. Reads through the graph are live, and a write, link or delete through it acts on the real record, exactly as through any other name holding it: `write f { … }` on a record reached through the graph updates it in its system, and a write into the graph's child edge whose `unique by` matches a referenced record updates that record. Such a write waits for every other write to the same record, as a write straight to it does, so concurrent `MAP` members merging into one record never lose an update. A write that matches nothing creates a new child in the graph, which stays in the run. The entry is typed as the records it holds, at any depth (a reference inside a child body, `attachment: { owner: r }`, too); with a shape they must carry what the shape's child node declares (`MOV_GRAPH_REFERENCE_SHAPE`, which points at the field-body copy). The edge keeps the walk's order where the walk has one, and a list's order. This brings back grouping records the run wrote under a named edge of a local record, then walking, filtering, linking onto and reporting them.
  - A walk followed by a field body and a record spread (`...r`) are the copies: snapshots, which a later change to the source does not reach. A file is copied as the handle it is, and nothing downloads.
  - A graph holding references to records read live from a system is refused by `TEXT.SERIALISE` at save (`MOV_STDLIB_ARG_NOT_RECORD`, naming the edge), as such a record is on its own; copy the fields with a field body to write it out. A run that parks keeps each reference as the record's handle, not a copy of its fields, and the resumed run reads it as it is then.
  - `lazy` inside a graph literal is a parse error naming the fix: a bare walk already reads live, and a walk to put off is a function (`files = () => m-[:Attachments]->`) called where it is needed.
  - `...v` converts a computed map (plugin output, JSON, a `{ … }` dict). With a shape, the shape decides whether a nested map is a child node or a value; a map nobody can type is checked against the shape when the graph is built, and the run fails naming the first field that doesn't fit. Without a shape every nested map is a child node, and a map whose keys are unknown is `MOV_GRAPH_SPREAD_UNTYPED`. Spreading something that is not a map is `MOV_GRAPH_SPREAD_NOT_MAP`. A graph literal takes its members in the order written, as a map literal and TypeScript's object literal do: a later field, child node or spread wins over an earlier one, so `graph<Note> { ...v, text: "mine" }` holds `"mine"` and `graph<Note> { text: "mine", ...v }` holds the spread's `text`. A key written before a spread that always supplies it is `MOV_MAP_KEY_OVERWRITTEN` (TypeScript's error 2783), whether the key is a field or a child node; a spread that may be absent overwrites nothing when it is, so it is no error.
  - The result reads by path, `WHERE` and dot, takes `write`, `link` and `delete` as a run-local node does, is a movement's return value, and fits a parameter of its shape.
  - `graph` is recognised only as `graph {` or `graph<Name> {`, neither of which was valid before, so an instance named `graph` (`listen to graph { … }`) keeps working and no language version changes.
- A hop `WHERE` on an edge of a node the run built now filters its landings (`msg-[a:attachment WHERE a.type = "application/pdf"]->`), in a block head and in an expression. Before, the run failed with an unsupported construct. A `WHERE` on a `lazy` entry's hop still fails the run.
- A list literal can spread a list into itself: `[m.Subject, ...m.Files, "end"]` splices the files in place, as TypeScript's `...` does, at the start, the middle or the end. Spreading something that is not a list (a text, a number, a record, a dict) is refused at save as `MOV_LIST_SPREAD_NOT_A_LIST`, and spreading a list that may be absent is `MOV_ABSENT_REQUIRED`; a value the checker cannot type that turns out not to be a list fails the run instead of splicing nothing.
- A walk read for a field can be spread into a list: `pdfs = m-[a:Attachments WHERE a.Type = "application/pdf"]->.\`File\`` then `[m.Body, ...pdfs]`, or inline `[m.Body, ...m-[a:Attachments WHERE …]->.\`File\`]`, splices one file per attachment the `WHERE` kept, and nothing when none did. Before, both were refused as `MOV_LIST_SPREAD_NOT_A_LIST`, because such a read is typed as one value of the field's type. It still is everywhere else, so a write field reading it behaves as before; only a spread now reads it as the values, as `COUNT` and `JOIN` already did. A field that itself holds a list spreads its members as before, and a `json` field is still refused, since one landing's list cannot be told apart from several landings. Nothing that validated changes, so no language version moves.
- A map literal takes spreads, as TypeScript's object literal does: `{ ...a, k: v, ...b }` copies a dict's keys, or one record's fields (its values, not its nested nodes), in the order written, and a later key wins. This is the plan's merge of an extracted record with its detail, `return { ...c, ...details }`. It applies under every language version, since a spread there was refused before.
  - A spread of a value that may be absent copies nothing when it is, as `...undefined` does, so the keys it supplies are `T | absent` (or joined with an earlier key's type).
  - A key written before a spread that always has it is `MOV_MAP_KEY_OVERWRITTEN`, as TypeScript refuses it: the spread overwrites it.
  - A spread of text, a number, a list, or a record read live from a system (whose fields the run does not hold) is `MOV_MAP_SPREAD_NOT_KEYED`. A settings record (`MAP`'s, `extract`'s, a built-in's options) is written out key by key, and refuses a spread.
- `graph<Shape> { ...r }` spreads one record into a graph literal, copying its fields as a snapshot, as TypeScript's `{ ...obj }` does: the shape decides which fields, a child node it declares is followed through the record's edge of the same name and copied in turn, files stay handles that download nothing, and nothing copied refers back to the record's system. `graph<Merged> { ...c, ...details }` is the merge as a record that can be walked and written into. Without a shape the record's own fields are copied. A record that may be absent copies nothing when it is, and its fields are `T | absent` against the shape. A map spread that is absent now copies nothing too, where it failed the run before. Before, a record spread was refused as `MOV_GRAPH_SPREAD_NOT_MAP`, which a list of records still is. This applies under every language version.

## 10. Waiting and resuming

- A run can now park and resume inside a called movement or closure, however many calls deep, and inside a collection op's member. Under Steady Lynx (3) a movement or closure that `await`s can be called on its own line or as the whole right-hand side of a binding (`answer = ask_partner(c)`): the run parks inside it, and when the wait ends the rest of the callee runs, its `return` comes back to the calling line, and that line goes on. Inside an expression the call is still refused (`MOV_NESTED_CALL_SUSPENDS`). Before, a wait inside a called movement parked at an address inside the callee's own body and the resume walked the dispatched movement's body from it, so the run came back to the wrong place; versions 1 and 2, which accept such a call, now resume it correctly too. A run parked that way before this release still resumes as it would have.
- Under Steady Lynx (3) the function of `MAP`, `FILTER`, `REDUCE`, `GROUPBY` and `KEYBY` may `await`. Why: the run can now resume inside a member, so a wait there has somewhere to come back to. A member that waits parks on its own while the others go on; a waiting member holds its place, so no more than `concurrency` members are in flight, and members not yet started run once the waiting ones finish. Resuming one member (a reply arriving for it) runs only that member. The op hands back its value, in member order, once every member has finished, and `onError` treats a member that fails after its wait exactly as one that fails without waiting. Under versions 1 and 2 such a function is still refused as `MOV_COLLECTION_OP_SUSPENDS`.
- Under Steady Lynx (3) a wait where a run cannot be resumed is refused at save as `MOV_WAIT_NOT_RESUMABLE`: an `await`, or a call to a movement or closure that awaits, inside a callback's body (`callback((x) => { … })`, or `callback(m)` for a movement `m` that waits), and a call to a function that awaits inside an `await until(…)` condition. Why: a fired callback's body and an `until` condition have no statement a resume can walk back to, so such a run parked where it could never be resumed (a callback body's wait failed when woken); version 3's lifting of the refusal on calling a function that waits had let the call through in these two places. Under versions 1 and 2 nothing changes.

## 11. Collection settings and write contention

- `MAP` and `FILTER` take a settings record between the collection and the function: `MAP(xs, { onError: "warn", concurrency: 4, initialConcurrency: 1 }, f)`. `onError` says what a member whose function fails does: `"error"` (the default) fails the run as before, `"warn"` leaves the member out of the answer and puts a warning naming it and the failure on the run's trace, and `"ignore"` leaves it out silently. A FILTER member whose predicate fails is not kept. Only the member's own failure is forgiven: a cancelled run, the call ceiling and a `match` that ends its scope behave as they always have. `concurrency` runs that many members at once; `initialConcurrency` runs a first batch of that size to the end before the rest start, so a shared prompt is cached once before the fan-out. The answer is in member order whatever order members finish in, and so is the trace. Members' writes run at once unless they contend for the same record: two members writing the same `unique by` key, or the target's own unique field, take turns, so the record is made once, while writes to different keys run together. A `FUZZY` key has no exact value to take turns on, so a fuzzy write takes turns with every identity write to its record type. Two updates of one record, a delete, and two links of one edge also take turns; a match, and a write with no identity at all, never wait. Each setting is written down, not computed; an unknown key, an `onError` outside its three values, a concurrency below 1 or not whole, and a first batch wider than the rest are refused at save as `MOV_COLLECTION_OP_CONFIG`. `REDUCE`, `GROUPBY` and `KEYBY` take no settings. Without a settings record nothing changes, so the language version does not either.

## 12. Cost cap and call depth

Operator detail; the settings themselves are described under "Automations" in [`deploy/SELF_HOSTING.md`](../../deploy/SELF_HOSTING.md).

- `MOVEMENT_MAX_RUN_COST_USD`, an optional cap in US dollars on what one automation run may spend on model calls and paid services. Once a run has spent it, the run PAUSES instead of failing: the part of the run that was about to make a priced call stops just before that statement, every other part of the run finishes the statement it is in and stops before its next, and a `MAP` starts no further member. `MAP`'s `onError` never sees the cap. The run shows as paused ("paused: cost limit reached", with what it spent and the cap, on `checkRun` and the runs page) and stays paused until someone resumes it: the Resume button on the runs page, the `resumeRun` tool, or `POST /v1/automation/automations/resume-run`. Resuming carries every stopped part on from exactly where it stopped (nothing it already did is done again) and resets the run's usage, so the cap applies afresh. A part of the run that was waiting for an answer, a timer or a reply stays waiting; if its event arrives while the run is paused it takes it and then stops before its next statement, until the run is resumed. Why pause rather than fail: a run that met its cap may hold a lot of finished work, and failing it threw that away. Two exceptions still fail: a rehearsal (dry run), which has nowhere to keep a paused run, and a fired callback's body, which a run cannot be resumed inside. A new platform event, `Run Paused`, tells other automations (`listen to sys { events: ["Run Paused"] }`); an automation is never told about its own runs pausing. The cap is the whole run's: a run that waits for an answer, a timer or an event and then resumes carries on from what it had already spent, so parking and resuming cannot escape it. A run started by another run has its own. Unset means no cap, and a value that is not a positive number fails boot. Not mandatory, but encouraged, since a looping automation is otherwise stopped by nothing; see "Automations" in `deploy/SELF_HOSTING.md` for what counts. Every run's step now records what it spent whether or not a cap is set: `costUsd` (this step), `runCostUsd` (the whole run so far) and `costBySource` (in microdollars, by where the money went: `model:<model>`, `service:brightdata.web_unlocker`, `plugin:<name>`); the run's own record sums the steps.
- `MOVEMENT_MAX_CALL_DEPTH`, how many calls deep one automation run may nest (default 32). A run that would go deeper fails, and its failure names the chain of calls (`call depth limit reached: 'intake → walk → walk → …' would nest 33 calls deep, and the limit set by MOVEMENT_MAX_CALL_DEPTH is 32`). Why: from Steady Lynx (3) functions may call themselves, and a recursion that never reaches the case that ends it would otherwise run until the process ran out of stack, or, making a priced call at every level, until the cost cap had been spent. `MAP`'s and `FILTER`'s `onError` never forgive it, as they never forgive the cost cap: it is the operator's safeguard, and forgiving it would let the setting silently change which items a `MAP` answers for. A value that is not a positive whole number fails boot. See "Automations" in `deploy/SELF_HOSTING.md`.
- A plugin can price its own work: it declares itself priced, so it is not started once its run has spent the cap, and its result may carry a cost (`{ microdollars }`, or `{ quantity, unit, unitPriceMicrodollars }`) that is charged to the run under the plugin's name. External functions will report cost in the same shape. Every bundled plugin is priced; page fetches through Bright Data's Web Unlocker are charged at $1.50 per 1,000 requests.

## 13. Diagnostic code index

The save errors authoring agents hit most carry a machine-applicable fix:

- The save errors authoring agents hit most now say the exact line to write, built from the automation's own text, and carry it as a `fix` (`{ edits: [{ line, col, endLine, endCol, text }] }`) on the diagnostic `validateAutomation` returns. A maybe-absent value in a write field (`MOV_ABSENT_REQUIRED`) gets `Name: COALESCE(<the expression>, "unknown")` (the fallback typed by the field: `0`, `false`, `[]`), plus `Name ?: <the expression>` where the field may be left unset; a field the write identifies its record by gets no fallback, since one value would merge every record written without it, and is told to gate the write instead. ## Appendix: every-version changes in full

These apply under every language version, as bug fixes or as widenings that accept only what was refused before. The changelog lists each in one line; this is the full text.

- In an `if` condition, `AND` now binds tighter than `OR`, as it does everywhere else: `if a OR b AND c` means `a OR (b AND c)`. Before, an `if` condition was split on every `AND` first, so it ran as `(a OR b) AND c`, while the same text as a value or in a hop `WHERE` meant `a OR (b AND c)`. A saved `if` condition that mixes `OR` and `AND` without parentheses now runs with the precedence it was written with. This applies under every language version rather than behind a version gate, ruled as a bug fix.
- `IF a AND b THEN … END` is accepted inside an `if` condition. Before, the same split cut it in half and the condition was refused.
- `IF(cond, a, b)`, written like a spreadsheet function, is refused saying how IF is written, with the rewrite: `IF cond THEN a ELSE b END`. Before, the message was whatever the parser tripped over next, such as "Unbalanced '}'" for a written field. A parenthesised condition (`IF (a OR b) THEN … END`) is unchanged. This applies under every language version; the form never parsed.
- Inside `EXISTS(…)`, a walk's `WHERE` can hold a `${…}` interpolation or another `EXISTS(…)`, and both are evaluated: `EXISTS(c-[p:Members WHERE EXISTS(p-[:Employer]->)]->)`. Before, both were left as a placeholder field that matched nothing. This applies under every language version.
- An email listen without a `key` is refused at save (`MOV_LISTEN_BAD_CONFIG`), with the fix: `listen to inbox { key: "intros" } fire …`. Why: the key is the plus-suffix of the address mail is sent to, and inbound mail finds its listener by that key alone, so a keyless listen saved with no address and could never fire. The requirement comes from the email adapter's own declaration of its routing key, so any adapter that routes inbound events by a key gets it. This applies under every language version rather than behind a version gate: such a listen never received anything. A Gmail listen, which reads a connected mailbox, needs no key and is unchanged.
- An empty hop `WHERE` (`crm-[c:Companies WHERE ]->`) is refused at save as `MOV_EXPR_PARSE`, saying to write a condition or drop the `WHERE`. Before, it was read as no filter, so the walk kept every record. This applies under every language version: an automation saved with one now fails at save and at run until the `WHERE` is written or removed.
- A `WHERE` on the final hop of a `match` or `write` target now narrows which existing records may be matched: `` match crm-[c:Companies WHERE EXISTS(c-[:Team]->)]-> { unique by (FUZZY `Name`), … } `` considers only companies with someone on their team. It used to be accepted at save and ignored at run. Each candidate the target's lookup returns is read as the record it is, the way a traversal's `WHERE` reads one (field reads, and hops such as `EXISTS(…)` or `COUNT(…)` from the candidate), and a candidate that fails is dropped before the identity is settled. A `write` whose candidates are all ruled out creates: the `WHERE` limits what may be updated, never whether to write. The save check now types the `WHERE` against the type the target lands on, and refuses it on a hop before the last (`MOV_TARGET_WHERE_NOT_FINAL`), on a `bind` write (`MOV_TARGET_WHERE_BIND`), and on an edge of a node the run built (`MOV_TARGET_WHERE_LOCAL`). This applies under every language version rather than behind a version gate: a saved `WHERE` said which records to match and was being ignored.
- A hop's `WHERE` reads the landed record through the hop's own alias as well as through a bare field: `` crm-[c:Companies WHERE c.`Categories` == "Customer"]-> `` now keeps exactly the companies that pass. The save check used to type the `WHERE` before the alias existed, so an unknown field read through it (`c.NoSuchField`) was not refused; it is now `MOV_UNKNOWN_PROPERTY`. At run time the alias was not bound while the `WHERE` was evaluated, so the hop failed with ``'c' is not in scope``. This applies to a hop heading a block, a hop inside an expression, and a hop inside `EXISTS(…)`. This applies under every language version rather than behind a version gate, like the target `WHERE` above: a saved `WHERE` that used the alias could not have run.
- A `unique by` test that is not part of the key (`WITHIN`, `!=`, a range) is honoured with several `unique by` lines: each line's test narrows the records its own key found. `` unique by (`Name`) `` plus `` unique by (`Domain`, `Updated` WITHIN 30d) `` no longer matches a stale record found by its domain. With two or more lines the test used to be dropped silently. A candidate missing a field the test reads is read in full first; a field the record still lacks fails the test, except `!=`, which it satisfies (before, such a candidate was kept whatever the test said). The save check refuses, as `MOV_UNIQUE_CONJUNCT_NEEDS_WHERE`, a test that reads anything but the candidate's own fields (a hop such as `EXISTS(…)`, a value from earlier in the run) and a `unique by` line with no key at all; the message points to a `WHERE` on the target. This applies under every language version rather than behind a version gate: each of these tests was written and then ignored.
- The arms of `await parallel([…])` and `await race([…])` no longer interfere with each other. Two arms calling the same movement are no longer refused as a recursion; each arm's trace entries read together, in arm order, rather than interleaved; and two arms writing the same `unique by` key make the record once instead of each creating it. An arm that fails now fails the combinator once the other arms have stopped, so what they did is recorded. The language version does not change: a run whose arms did not contend does exactly what it did.
- A `return` always leaves its body, including after the run parks on it. Before, a `return await sleep(…)` that woke went on to the statement after it: in an `if` arm, the code below the `if` ran; in a function, the function's later statements ran and their value was returned instead. A `return` of a traversal-headed block or of `await race(…)`/`await parallel(…)` that parked could not be resumed at all. A `return` whose value turns out absent also returns, as an absent value, and the engine no longer decides whether a body returned by looking at the value. This applies under every language version, as a bug fix.
- A traversal-headed block or an `await parallel([…])` that parked on some of its iterations or arms while others finished now keeps what the finished ones returned: the bound value after the resume holds every iteration's return and every arm's slot. Before, only the parked ones' came back, so the finished ones' values were missing from the list and their receipt slots were empty. This applies under every language version, as a bug fix.
- `x = await sleep(…)` (and `return await sleep(…)`) binds `true` after the timer really wakes. Before, a woken sleep bound nothing (null) because the resume's empty answer shadowed the wake marker, so `x` read as false.
- A node the run built keeps its identity when the run parks. One node held in two places (two graphs referencing it, or two names bound to it) comes back as one node after the resume, so a write through one is seen through the other; before, each place got its own copy. A node linked to itself, or two nodes linked to each other, now park and resume as the same cycle; before, the park failed with a stack overflow. A run parked before this release resumes as it did, each place with its own copy. This applies under every language version.
- `MAP` over an edge of a node the run built that holds a system's records (a node literal's walk, a graph literal's reference) now reads their fields. Before, each member reached the function as a bare position and every field read off it came back empty. This applies under every language version.
- A file bound before a run parks (an email's attachment in `files = COLLECT(m-[:Attachments]->.File)`, or a list holding it) can be read again after the run resumes, whether it waited on a timer, an `await`, a callback, or a cost-limit pause. Before, the file came back with its name but no way to fetch its bytes, so an `extract(…)` or `READ(…)` after the resume went on without it: an extraction's input silently lost the attachment's text. The parked file now keeps its source's handle, as a file crossing to a remote adapter does, and the resume fetches the bytes through the system it came from. A run parked before this release resumes with its files readable too. A file whose bytes the run cannot fetch now puts a warning on the run (`MOVENG_FILE_BYTES_UNAVAILABLE`, once per file) as well as on the trace of what read it; the read still goes on, telling the model the file could not be read. A value holding any other function is refused at park rather than dropped. This applies under every language version.
- A run's trace now shows the records an `extract(…)` or `extractOne(…)` call found, as it already did for the `extract` keyword: the call's trace entry lists each record's fields by node name (nested records under their own name), capped at 20 per name with the rest counted. Nothing is shown for an `extractOne` that found nothing. This applies under every language version.
- A run's trace for an `extract(…)` call now says what the model answered, as the `extract` keyword's does. Its count is the records the model answered with, with `empty` and `dropped` beside it (so the run page's "N (k dropped)" means the same on both), and a call that returned no records, dropped one, was asked again or failed keeps a capped digest of the reply, so "the content did not say" can be told from a malfunction.
- The cost-limit pause message shows a small limit as it was set: a `MOVEMENT_MAX_RUN_COST_USD=0.016` limit reads `$0.016`, not `$0.02`, and the spend beside it keeps up to four decimals.
- `TEXT.SERIALISE` of a value holding a `lazy` edge that has not run (`TEXT.SERIALISE(node { items: lazy a-[f:…]-> }, 'JSON')`) is now refused at save as `MOV_STDLIB_ARG_LAZY_EDGE`, saying to read the walk first. Before, it saved and failed when the movement ran. Nothing that ran changes.
- A library file that does not parse is reported with its position once; the `MOV_IMPORT_FILE_INVALID` message named the line twice.
- An inbound email's `Body` strips HTML even when the markup arrived in the message's plain-text part rather than its HTML part (seen from a mail-merge forwarder); genuine plain text with a stray angle bracket is left unchanged, and `Plain Body` / `HTML Body` still carry the raw parts exactly as delivered.
- `TEXT.SERIALISE(value, "JSON")` writes any value out as text for a prompt, byte for byte the same whenever it is the same value: two-space indented JSON with keys sorted at every level, so the order fields were written in never shows. A record is its fields plus its nested nodes under their edge names, each edge always a list; dicts and lists nest as themselves; an absent value is `null`; dates are ISO text; a file is its name, type and size, never its contents. The format is written down: an unknown or computed one is refused at save (`MOV_STDLIB_ARG_INVALID`, `MOV_STDLIB_ARG_NOT_LITERAL`), as is a record read live from a system (`MOV_STDLIB_ARG_NOT_RECORD`). Nothing existing changes meaning, so no language version moves.
